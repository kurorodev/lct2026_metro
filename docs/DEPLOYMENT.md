# Деплой на Ubuntu 24.04: 2 ГБ RAM, диск 20 ГБ

> **Для жюри.** Публичная веб-версия позволяет открыть просмотрщик проекта по [ссылке](http://111.88.155.2/); полный [исходный код](https://github.com/kurorodev/lct2026_metro) открыт на GitHub. Сервер раздаёт подготовленные результаты: обработка записи запускается отдельно.
>
> Локальную демонстрацию можно запустить по [короткой инструкции](../README.md#локальный-запуск). Этот документ описывает самостоятельную публикацию проекта на Ubuntu.

Подготовлен серверный режим для обработки **одного бэга за раз** и просмотра результатов в браузере. Он использует `Dockerfile.server` (Python 3.11 без ROS) и `compose.yaml` (обработчик + Nginx). По умолчанию просмотрщик публикуется на `0.0.0.0:80`, поэтому открывается как `http://SERVER_IP/` после освобождения порта старым сайтом.

Это готовность инфраструктуры к исследовательскому использованию. Детектор по-прежнему даёт ложные тревоги на объектах вне предполагаемого габарита; точный контур состава неизвестен. Деплой не устраняет эти ограничения, описанные в [отчёте](FAKE_SCENARIO_RESULTS.md).

## Ресурсы и данные

| Компонент | Параметр |
|---|---|
| Обработчик | 1 CPU, максимум 1 ГиБ памяти вместе с файловым кешем, swap контейнера отключён |
| Nginx | до 0,5 CPU, максимум 64 МиБ памяти |
| Серверный образ | около 269 MB в проверенной ARM64-сборке |
| Новый bag после распаковки | около 6,9 ГиБ |
| Его архив | около 1,6 ГиБ дополнительно |
| Весь старый набор после распаковки | около 22 ГиБ — **не помещается** на диск 20 ГБ вместе с ОС |
| Предпросмотр нового бэга | около 19 МБ, 151 кадр по максимум 2000 точек |

До переноса нового архива оставьте минимум **10 ГиБ свободного места** (`df -h`). Это запас для архива, распаковки, образов и результатов; 20 ГБ общего размера диска не означают 20 ГБ свободного. Для старых записей переносите только выбранный распакованный каталог bag. Не копируйте на сервер все `data/`, `outputs/` или локальную `.git`: они могут занимать десятки гигабайт. Бэги не включены в Git и Docker-образ.

Тестовый полный прогон `cloud_with_fake_obj` завершился с 1510 кадрами, лимитом 1 ГиБ/1 CPU и `OOMKilled=false`. Проверка выполнена в локальном Linux ARM64 Docker; скорость CPU вашего сервера и AMD64-сборка здесь не измерены. В CI добавлен отдельный запуск на Ubuntu 24.04. Поле `peak_rss_mib` в новых `summary.json` показывает пик RSS процесса, без файлового кеша cgroup.

Также полностью обработан `doubleT_obstacle` (201 кадр, наиболее крупные облака из старого набора): выход 0, без OOM, пик RSS **242,7 МиБ**. Это проверка конкретных записей, а не гарантия для облаков произвольного размера. Автоматические тесты: 23 проверки ядра, оценки и публикации файлов; интеграционный серверный тест включает HTTP, блокирование незавершённого экспорта и сохранность данных после перезапуска web.

## Подготовка сервера

Установите [Docker Engine и Compose plugin для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) и включите запуск Docker при загрузке. Далее команды выполняются пользователем, у которого уже есть доступ к Docker:

```bash
sudo apt-get update
sudo apt-get install -y git python3 zstd
sudo systemctl enable --now docker
docker version
docker compose version
df -h .
free -h

git clone --depth 1 https://github.com/kurorodev/lct2026_metro.git
cd lct2026_metro
./scripts/server.sh init
```

Нужен современный Compose plugin с `up --wait` и `config --format json` (Compose 2.20+ либо 5.x); старый отдельный `docker-compose` не используется. `init` создаёт `.env` из `.env.example`, подставляет UID/GID пользователя и создаёт `data/` и `outputs/`. Существующий `.env` не изменяется. Он исключён из Git. Для обычного пользователя контейнеры также работают без root; если запускать init от root, `.env` будет содержать UID 0. Предпочтителен отдельный пользователь деплоя; владельцы `outputs/` должны совпадать с `APP_UID:APP_GID`.

## Перенос нового бэга

С машины, на которой находится архив (замените пользователя, хост и путь):

```bash
scp data/cloud_with_fake_obj.zst USER@SERVER:/home/USER/lct2026_metro/data/
```

На сервере из корня проекта:

```bash
tar --zstd -xf data/cloud_with_fake_obj.zst -C data
ls -lh data/cloud_with_fake_obj/
```

Ожидаются `metadata.yaml` и `cloud_with_fake_obj_0.db3`. После успешной распаковки и проверки архив на сервере можно удалить для освобождения 1,6 ГиБ; исходный архив на вашей машине останется. Повторно архив скачивать для каждого запуска не требуется.

## Сборка, обработка, просмотр

Настройки `.env` по умолчанию выбирают новый бэг, `config/mounted_lidar.json` и порт 80:

```bash
./scripts/server.sh check
./scripts/server.sh build
./scripts/server.sh run
./scripts/server.sh up
./scripts/server.sh status
```

`run` — конечная задача: читает bag, записывает результат и завершается. `up` запускает постоянный веб-сервис и ждёт успешного healthcheck. Обработчик не перезапускается бесконечно после завершения. Веб-сервис автоматически запускается снова после перезапуска Docker/сервера (`unless-stopped`). Результаты остаются в `outputs/cloud-mounted/`, независимо от жизненного цикла контейнера.

Для длительной задачи, если SSH может оборваться, можно запустить её отдельно:

```bash
docker compose run -d --name metro-batch processor
docker logs -f metro-batch
docker inspect metro-batch --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
```

После завершения ожидаются код 0 и `false`, затем выполняйте `./scripts/server.sh up`. Именованный контейнер сохраняется для проверки логов; перед следующим запуском с тем же именем удалите **завершённый** контейнер командой `docker rm metro-batch`.

После успешного `up` откройте `http://SERVER_IP/`. Если созданный ранее `.env` всё ещё содержит старые значения, измените его на `BIND_ADDRESS=0.0.0.0` и `HTTP_PORT=80` (`init` существующий файл не перезаписывает).

`./scripts/server.sh check web` предупредит, если порт 80 занят. Найдите старую службу командой `sudo ss -ltnp 'sport = :80'`; Docker контейнер — `sudo docker ps --format '{{.Names}} {{.Ports}}'`. Остановите старый веб-сервис, сохранив SSH, Ubuntu и Docker, затем повторите `check web` и `up`. Если включён UFW, разрешите HTTP: `sudo ufw allow 80/tcp`; если у хостинга есть внешний firewall, разрешите TCP/80 и там.

На порту 80 нет TLS и встроенной авторизации: любой посетитель сервера сможет просматривать и скачивать экспортированные данные. Для публичного домена настройте HTTPS и аутентификацию на reverse proxy. Если пока нужен только приватный доступ, задайте в `.env` `BIND_ADDRESS=127.0.0.1`, `HTTP_PORT=8080`; затем откройте туннель `ssh -N -L 8080:127.0.0.1:8080 USER@SERVER` и зайдите на `http://localhost:8080`.

Просмотрщик показывает уже обработанную запись и поддерживает 3D, переключение кадров и разметку. Загрузки бэга и запуска детектора через браузер нет; метки можно сохранить на компьютер кнопкой JSONL.

## Другие бэги и повторные прогоны

В `.env` измените:

```dotenv
BAG_NAME=for_hackathon/doubleT_obstacle
RUN_NAME=doubleT-mounted-20260928
CONFIG_FILE=./config/mounted_lidar.json
```

В `DATA_DIR` должны лежать только нужные записи. `BAG_NAME` — путь относительно `DATA_DIR`, `RUN_NAME` — имя каталога внутри `OUTPUT_DIR`. Затем `./scripts/server.sh run` и `./scripts/server.sh up`. При изменении `RUN_NAME` Compose пересоздаст web с новым каталогом. Для переключения между готовыми результатами достаточно сменить `RUN_NAME` и выполнить `up`, повторно обрабатывать не нужно.

Для каждого нового прогона используйте новое имя. Повторная запись требует явного `--overwrite` в CLI. Не перезаписывайте результат, который в это время просматривают пользователи: файлы обновляются по отдельности, поэтому согласованность нескольких HTTP-запросов при обновлении одного каталога не гарантируется. Разные каталоги позволяют сохранить предыдущий результат и быстро вернуться к нему.

`EXPORT_EVERY=10` и `PREVIEW_POINTS=2000` ограничивают только браузерный экспорт; детектор обрабатывает все точки каждого кадра. Если длинная запись создаёт `frames.json` больше 64 МиБ, preflight веб-сервиса попросит увеличить интервал или уменьшить число точек и выполнить новый прогон. Не переносите прежний файл `frames.full.json` размером 1,1 ГБ как основной предпросмотр.

Оценщик и скрипты анализа тоже входят в лёгкий образ (включая Pillow). Например, для оценки результатов по загруженной разметке:

```bash
docker compose run --rm --entrypoint python processor -m metro_guard.evaluate \
  /output/cloud-mounted/detections.jsonl /data/labels/reviewed.jsonl \
  --output /output/metrics.json
```

Разметку предварительно перенесите в `data/labels/`; её отсутствие не заменяется предсказаниями детектора. Дополнительные утилиты запускаются аналогично с `--entrypoint python` и путями `/data` (чтение) / `/output` (запись).

## Контроль работы и обновление

```bash
curl -f http://127.0.0.1/healthz
curl -f http://127.0.0.1/readyz
./scripts/server.sh status
./scripts/server.sh logs
docker stats --no-stream
df -h .
```

`healthz` проверяет ответ Nginx; `readyz` — наличие опубликованных файлов и отсутствие незавершённой публикации. Они не оценивают качество детекции. При штатной ошибке чтения bag новые частичные результаты не публикуются, старый успешный результат сохраняется. Параллельная запись двух процессов в один выходной каталог запрещена файловой блокировкой. При убийстве процесса могут остаться скрытые `.pending-*` каталоги; перед их ручной очисткой убедитесь, что обработка уже не идёт.

Логи Docker ротируются: до трёх файлов по 10 МБ на контейнер. Удаление контейнера не удаляет bind-mounted данные. `summary.json` содержит полный конфиг и его SHA256; вместе с `detections.jsonl` это основа воспроизводимости запуска.

Обновление кода и образа:

```bash
# Сначала дождитесь завершения текущей обработки.
git rev-parse HEAD                 # сохраните этот commit для отката
docker tag metro-guard:server metro-guard:previous
git pull --ff-only
./scripts/server.sh build
# Задайте новый RUN_NAME в .env, затем:
./scripts/server.sh run
./scripts/server.sh up
```

Откат результатов: верните прежний `RUN_NAME` и выполните `up`. Для обработки прежним образом задайте `METRO_IMAGE=metro-guard:previous` в `.env`, восстановите соответствующий конфиг и выберите новое имя результата. Изменения файлов Compose/Nginx тоже хранятся в Git; при необходимости восстанавливайте их из сохранённого коммита. Не запускайте `build` с тегом `previous`, если хотите сохранить резервный образ.

## Самопроверка без исходных данных

```bash
./scripts/server.sh build
bash scripts/server_smoke.sh
```

Проверка создаёт небольшой синтетический ROS 2 bag, обрабатывает его, запускает отдельный Compose-проект на localhost:18080, проверяет HTTP и подтверждение препятствия, имитирует незавершённую публикацию, перезапускает web и снова проверяет данные. Контейнеры проверки убираются автоматически; небольшой fixture остаётся в `outputs/server-smoke.*`. Основной веб-сервис не останавливается. Другой порт задаётся `SMOKE_PORT=18081`.

## ROS 2 и живой LiDAR

Исходный `Dockerfile` и `scripts/entrypoint.sh` сохранены для ROS 2 Humble, playback и RViz. Этот образ работает с Ubuntu 22.04 внутри контейнера; устанавливать Humble непосредственно в Ubuntu 24.04 не требуется. На сервере 2 ГБ основной профиль специально использует лёгкий офлайн-образ. Живой режим требует отдельной проверки DDS, сети датчика, очередей и задержек на самом сервере; эта конфигурация не объявляет его проверенным.

Описание ROS-запуска находится в [руководстве проекта](PROJECT_GUIDE.md#ros-2-узел-и-rviz). Чтобы применить новую установку датчика, передайте узлу `--ros-args -p config_path:=/app/config/mounted_lidar.json`. Офлайн-режим читает те же ROS 2 bag напрямую и не нуждается в запуске ROS.

Технические основания: [Compose: ограничения, restart, healthcheck и volumes](https://docs.docker.com/reference/compose-file/services/), [Nginx: раздача статических файлов](https://nginx.org/en/docs/http/ngx_http_core_module.html). Команда `metro_guard.cli serve` остаётся для локальной разработки; [Python не рекомендует http.server для production](https://docs.python.org/3/library/http.server.html).
