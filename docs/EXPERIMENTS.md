# Эксперименты

> **Для жюри.** Замеры показывают, что код обрабатывает предоставленные записи и проходит интеграционный путь ROS 2. Они **не доказывают точность обнаружения**: пока нет независимой покадровой разметки и подтверждённого габарита поезда.
>
> **Проект:** [публичный код](https://github.com/kurorodev/lct2026_metro) · [веб-демонстрация](http://111.88.155.2/). Локальный запуск воспроизводится по [короткой инструкции](../README.md#локальный-запуск).

Ниже приведены условия измерений, сравнительные результаты и границы их интерпретации.

## Среда и объём

macOS 15.6.1, ARM64, Python 3.8.20, CPU без GPU. Это не целевой Intel-стенд и не Windows-ПК пользователя. Одна конфигурация для всех шести bag; обработаны все 2488 кадров. Для просмотра экспортирован каждый пятый кадр и до 3000 точек. Прореживание касается только визуализации.

## Частота тревог — не качество

| Bag | Кадры obstacle | Всего |
|---|---:|---:|
| doubleT_obstacle | 177 | 201 |
| doubleT_platform | 343 | 345 |
| roundT_doubleT | 166 | 252 |
| roundT_pressureGate_roundT | 226 | 268 |
| roundT_squareT_pressureGate_squareT | 341 | 545 |
| squareT_platform_squareT_switch | 765 | 877 |

**Большая доля тревог на записях с платформами и обычным тоннелем — причина не считать детектор готовым к финальной сдаче по качеству.** Визуальный анализ показывает кандидатов на инфраструктуре, особенно на дальних изгибах и у платформ. Нужны калибровка, корректная оценка пути и независимая разметка.

Без ground truth нельзя назвать эти числа precision, recall или false positive rate. `quality_metrics` оставлены null. Расстояния до кластеров не выдаются за доказанную дальность обнаружения настоящих препятствий.

## Автоматические проверки

18 unit-тестов: padded/big-endian PointCloud2, реальная 26-byte структура, поворот осей, пустые/нечисловые точки, пустой прямой/изогнутый тоннель, рельсы и низкая боковая площадка, потолок, объект на 25 m, временное подтверждение, сброс при разрыве/откате времени, разделение кластеров и правила подсчёта метрик. Все прошли локально и при сборке Docker.

Docker: Ubuntu 22.04 / ROS 2 Humble, Linux ARM64 на текущей машине. Базовый образ закреплён manifest digest, Python-зависимости закреплены версиями. apt-зависимости устанавливаются из репозитория ROS/Ubuntu; для побитовой воспроизводимости нужно дополнительно архивировать собранный образ. Установка Python-пакета проверена импортом из `/tmp`, чтобы импорт из `/app` не маскировал сломанный wheel.

ROS-интеграция: `scripts/ros_smoke.py` публикует PointCloud2 через DDS, ожидает подтверждение синтетического объекта на 25 m, проверяет облака/маркеры и watchdog после остановки потока. Результат — passed. Это проверка тракта, не реальной точности.

Первый `ros2 bag play doubleT_obstacle` дал только 97 результатов из 201 кадров и 14 замен в очереди. Потери нельзя приписать только детектору: счётчик очереди не учитывает DDS/discovery. После увеличения SHM и ускорения упаковки облака для RViz до callback дошли все 201 сообщения; при очереди 1 кадр обработан 161, остальные 40 заменены. Увеличение очереди до двух кадров и получение raw CDR проверены отдельно.

**Финальный ROS-прогон версии 0.2.0:** получены и обработаны все 201 сообщение, вытеснений из очереди — 0; p95 от callback до результата 62.9 ms. Подписчики облаков и маркеров включены, p95 подготовки визуализации 0.98 ms. Запись охватывает 20.400 s, интервал поступления сообщений — 20.249 s. Проверка выполнена на Linux ARM64 в Docker, не на целевом Windows/x86 ПК.

Причина прежних потерь обнаружена в профиле воспроизведения: после стартовой задержки rosbag догонял время и выдавал сообщения пачками. В demo и интеграционном тесте установлены `--read-ahead-queue-size 2 --delay 1`; очередь детектора остаётся ограниченной двумя кадрами. rosbag предупреждал об опустошении очереди чтения и задержках; отсутствие потерь в этом прогоне не означает жёсткого соблюдения каждого периода 100 ms. Журналы окончательной проверки: `analysis/ros-real.log`, `analysis/ros_validation.json`. Предыдущие измерения сохранены для сравнения.

Браузер: headless Chrome, реальные экспортированные кадры, переключение вида и кадра; desktop 1600×1080 и mobile 390×844, без горизонтального переполнения и JS-исключений. Доказательства: `analysis/browser_check.json`, `analysis/dashboard.png`, `analysis/dashboard-mobile.png`.

Историческая проверка до исправления воспроизведения с подписчиками визуализации: очередь 2 дала 159 обработанных кадров, 42 вытеснения и p95 76.8 ms; визуализация занимала около 1.1 ms (p95). Очередь 4 дала 163 кадра и p95 121.2 ms. Увеличение очереди не устраняет основное ограничение, поэтому очередь детектора оставлена равной 2; позднее исправлена буферизация воспроизведения, как описано выше. Визуализация ограничена 5 Hz и отключается при отсутствии подписчиков; это экономит работу, но не объявляется решением всех потерь. Данные сравнений сохранены в `analysis/ros_queue_comparison.json`.

## Демонстрация

`analysis/demo.webm` — запись визуализации всех 41 экспортированных кадров `doubleT_obstacle` с временными интервалами bag. На видео явно указано, что точность не валидирована. Это запись офлайн-просмотра; живой ROS-путь проверен отдельно интеграционными тестами.

## Что пока не измерено

- Precision/recall на реальных объектах, событийные пропуски, ложные тревоги в час.
- Доказанная дальность обнаружения по размерам/типам препятствий.
- Обобщение на скрытые проезды и независимые участки.
- Работа RViz GUI на стенде и запуск на Windows/RTX 5070 Ti.
- Тормозной путь, скорость поезда, безопасность принятия решения.

Следующая проверка качества должна использовать независимые метки и фиксированный отложенный проезд. Параметры не должны подстраиваться под имя контрольного bag.

## Экспериментальная оценка пути по рельсам

`config/rail_guided.json` проверен отдельно на всех 2488 кадрах. Число кадров obstacle: 73, 258, 112, 89, 175, 231 соответственно порядку bag в таблице выше. Уменьшение тревог затронуло также `doubleT_obstacle`, поэтому улучшение качества не установлено. Основной конфигурацией оставлен baseline: его распределение статусов совпадает с предыдущей версией на всех шести записях. Результаты: `outputs/rail-guided-v2/benchmark.json` и `outputs/release/benchmark.json`.

Калибровки и габаритов поезда у пользователя нет. Геометрия остаётся предположением, оцениваемым по облакам. В интерфейс добавлена ручная разметка с возможностью скрыть предсказания; экспорт JSONL пригоден для независимой оценки. Неоднозначные кадры можно оставлять без определённого ответа. Автоматические предсказания не считаются эталоном.
